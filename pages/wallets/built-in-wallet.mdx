# The Built-In Wallet

Superhero can create and hold an æternity account inside the app itself, with no extension and no
second app. The seed lives encrypted in your browser's own storage on that device, and every
signature re-verifies you before the seed is decrypted.

It is a different thing from [Superhero Wallet](/wallets/superhero-wallet-extension), the
standalone extension and mobile app, though both hold the same kind of `ak_...` account.

## Where it is offered

| Surface | Create a wallet | Import an existing seed | In-page signing |
| --- | --- | --- | --- |
| Installed PWA (Add to Home Screen) | Yes | Yes | Yes |
| Plain browser tab | Yes | Use Connect | Signing goes through the connected wallet |

Creating a wallet (passkey or a fresh recovery phrase) is offered on every surface. Pasting a seed
phrase or private key is offered **in the installed app**. In a browser tab, "I already have a
wallet" means Connect, which hands signing to the extension or the wallet app and never asks for
your secret.

The in-page signer is installed only when the app is running installed *and* the active address
belongs to this device's wallet. An externally connected wallet is never intercepted.

## How the key is stored

```text
mnemonic (BIP39, 12 or 24 words)
   │  encrypted (AES-256-GCM)
   ▼
sealed under a random data-encryption key (DEK)
   │
   ▼
one wrapped copy of the DEK per enrolled factor  ── passphrase · recovery code · passkey
```

One encrypted vault record per device. Every secret inside it is ciphertext; nothing is sent to a
Superhero server.

Factors form an **OR-set**: any single enrolled factor unwraps the same DEK and opens the whole
vault. That is what makes "passkey or passphrase" work, and it is why **every factor you enroll
should be a strong one**: each of them opens the vault on its own. A vault always keeps at least one
factor.

## The unlock factors

| Factor | How the key is derived | Where the secret lives |
| --- | --- | --- |
| Passphrase | Argon2id (memory-hard, so an offline attack on a copied vault is expensive) | Your head |
| Recovery code | HKDF from 128 generated bits | Wherever you wrote it |
| Passkey | HKDF from the WebAuthn PRF output | Your platform authenticator |

### Passphrase

The passphrase is scored locally with zxcvbn, with no network call. The rules:

- Minimum zxcvbn score **3** of 4 ("safely unguessable").
- A numeric-only string is rejected as a PIN.
- The generator offers **five words from the BIP39 English list**, about 55 bits.
- If the estimator has not loaded, Create waits and you are offered a retry.

To change the passphrase, recreate the wallet from the recovery phrase. See
[Backup & Recovery](/wallets/backup-and-recovery).

### Recovery code

A 128-bit code shown **once** at enrollment, rendered as eight dash-separated groups of four
uppercase hex characters. Parsing tolerates case, spaces and dashes.

The recovery code is **passkey-independent**: it unwraps the DEK inside this device's vault record,
so it unlocks the wallet on the device where it was created. For a new device, use the written
phrase or a syncing passkey.

### Passkey

The passkey factor uses the WebAuthn **PRF extension**, which yields a stable 32-byte secret for a
given credential. The ceremony requires user verification and a resident (discoverable) credential.

The passkey factor needs a PRF result from the authenticator. If the first ceremony returns no PRF
output, the app runs a follow-up assertion to obtain it, which is why you may see two prompts.

The Relying Party ID is pinned at build time from `VITE_WEBAUTHN_RP_ID` and defaults to
`superhero.com`, so a bundle served from another host has no access to your Superhero passkey. If
that value does not match the origin, the passkey option stops before the OS prompt. See
[Troubleshooting](/wallets/troubleshooting).

## Two ways a wallet is created

### From a recovery phrase

A 12-word BIP39 phrase is generated, shown, and **verified by re-entry** before any vault exists.
Then a passphrase factor creates the vault. The recovery code is enrolled next and is mandatory. A
device passkey is offered after that and is optional.

Import follows the same path minus the show/verify screens. The phrase is normalized (trimmed,
whitespace collapsed, lowercased) and checked against the BIP39 wordlist **and checksum** before a
vault is created, so a typo is caught before anything is stored.

### From a passkey

One ceremony does everything. The passkey is enrolled, and the BIP39 mnemonic is **derived from its
PRF output** at a fixed, public salt, so creation completes in one step. The seed derivation and the
key that wraps the DEK use separate derivations, so neither can be computed from the other.

The salt is fixed rather than random so that the seed can be re-derived on any device the passkey
reaches, even after the vault is gone. That makes a **syncing** passkey (iCloud Keychain, Google
Password Manager) a real backup. A device-bound platform credential such as Windows Hello stays on
its device, and **the passkey is the copy of the seed for this wallet**, so choose a syncing
credential and enroll the recovery code.

**Restoring on a new device** runs a discoverable assertion, derives the wallet the credential
implies, and shows you the derived address **before persisting anything**. The confirm screen also
checks whether that address has on-chain activity: an account with no activity is a sign that you
picked a different passkey, because a phrase-created wallet's device passkey evaluated at the seed
salt derives a different, empty wallet. Go back and choose again.

## Key derivation

| Purpose | Path | Curve |
| --- | --- | --- |
| æternity spending key | `m/44'/457'/<index>'/0'/0'` | ed25519, SLIP-0010 |
| Nostr chat identity | `m/44'/1237'/0'/0/<index>` | secp256k1 |

The æternity path uses the SDK's own account factory, so an account created here is
**byte-identical** to importing the same phrase into the Superhero Wallet extension or the native
app at the same index. You can move between them freely.

## Signing

Every signature runs the same sequence, with no fast path:

1. Run the unlock (a WebAuthn ceremony or the passphrase prompt). This happens on **every signature.**
2. Unwrap the DEK, unseal the mnemonic, derive the account key. All transient.
3. Check that the derived key produces the advertised address. If not, **refuse to sign**.
4. Sign, then drop every reference.

Nothing is cached between signatures: the vault record is reloaded from storage on every signature,
so adding a factor takes effect immediately. One prompt renders at a time, and a signing request
that arrives with no confirmation prompt mounted is answered immediately with a rejection.

**The chat identity is the one cached key.** The Nostr chat key is derived through the same unlock
path and then cached in memory for a **rolling 30-minute idle window**; chat activity resets the
timer, and the key is dropped when it expires or on an explicit lock. The unlock prompt says so.
Nothing else derived from the seed is cached. The unlock returns Nostr keys only, never the
mnemonic, the DEK or the æternity spending key.

### What the confirmation shows

The transaction is decoded into named rows, with two deliberate behaviours:

- **Decode, never re-encode.** The bytes signed are always the original string, so what you
  approve is what is sent.
- **Fail closed.** If the envelope, a contract call's arguments, or a wrapped inner transaction
  does not decode, the prompt **withholds approval**, so you sign what you can read.

Recognised calls are named in plain language: publish a post, buy tokens, sell tokens, create a
community, transfer, the four AEX-9 allowance operations, add and remove liquidity, wrap and
unwrap AE, add a poll, cast or revoke a vote, delegate and revoke delegation, and the
invitation-code operations. A call whose argument shape does not match is shown as an unrecognised
contract call with every argument rendered raw.

Two rows to read every time:

- **"Gas, at most"**: gas is charged on top of the network fee, so read both rows for the full cost
  of a contract call.
- **"Name price"**: on a name claim this is the largest amount by far.

Token amounts are shown in **raw base units, not scaled by decimals**, so the figure matches the
on-chain call exactly. Count the digits against the token's decimals.

## Where the key material lives

| Thing | Where | Encrypted? |
| --- | --- | --- |
| The vault record (sealed mnemonic, wrapped DEKs) | IndexedDB, database `superhero-wallet`, store `vault`, key `vault` | Yes |
| Wallet manifest (addresses, derivation indexes, labels, active address) | `localStorage`, key `wallet.inlineManifest` | No, public data only |
| Mnemonic, DEK, derived keys | Memory, inside one unlock-to-sign scope | n/a |
| Anything at all | A Superhero server | Nothing is sent |

## Site data and your backup

**The vault record lives in the site data for superhero.com, and clearing site data (or "Cookies
and site data") removes it.** The passphrase, the recovery code and, on a *phrase-created* wallet,
the device passkey each unwrap a key inside that record, so they unlock the wallet on this device
while the record is present. For restoring anywhere, keep the written phrase or a syncing passkey.

Browsers can also evict IndexedDB on their own; Safari's Intelligent Tracking Prevention can do so
after roughly seven days without interaction. Treat the written phrase or the syncing passkey as
the backup, and the vault as the copy on this device.

What restores the wallet after the vault is gone:

| You have | Restores? | Why |
| --- | --- | --- |
| The written 12/24-word phrase | **Yes** | Standard BIP39 on the standard path, so it re-imports anywhere. |
| A **syncing** passkey on a passkey-created wallet | **Yes** | The seed re-derives from the PRF output at the fixed public salt. |
| A device-bound passkey (e.g. Windows Hello) on a passkey-created wallet | On that device | It stays on the device it was created on. |
| A passkey on a **phrase-created** wallet | No | It wraps a DEK rather than deriving the seed. |
| The recovery code alone | No | It unwraps a DEK rather than deriving the seed. |
| The passphrase alone | No | It unwraps a DEK rather than deriving the seed. |

If only `localStorage` is cleared, unlock once and the app rebuilds the manifest by re-deriving
addresses from index 0 upward.

Erasing the wallet deliberately is available from the "this device already has a wallet" screen and
takes two taps. Confirm your written phrase or syncing passkey before you erase.
