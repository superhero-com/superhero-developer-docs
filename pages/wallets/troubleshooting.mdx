# Wallet Troubleshooting

Find your symptom and apply the fix.

## Passkeys

### Tapping the passkey option does nothing

The WebAuthn Relying Party ID for wallet passkeys is pinned into the build from
`VITE_WEBAUTHN_RP_ID`. If that pinned value is not a registrable domain suffix of the origin you are
on, the browser stops the ceremony with a `SecurityError` before the operating system shows a
prompt.

| Where you are | Correct `VITE_WEBAUTHN_RP_ID` | Passkeys work? |
| --- | --- | --- |
| `superhero.com` (production) | `superhero.com`, the default | Yes |
| Local dev on `localhost` | `localhost` | Yes, when set |
| Any other origin | A registrable suffix of that origin | Yes, when set for that build |

**Fix:** on production, report it. On any other origin, rebuild with the right
`VITE_WEBAUTHN_RP_ID`, or use a recovery phrase instead.

The app catches this exception and shows *"Passkeys aren't available on this domain (this build
expects …). Use a recovery phrase instead."* The name it prints is the RP ID the build was
compiled with. The DOM exception name and message are also written to the browser console; include
them in any report.

### The passkey prompt appeared, then the wallet did not open

The ceremony ran and the derived key did not match this vault, so the unlock stopped. Two common
causes:

- **You picked a different passkey** from the OS list. Retry and choose the Superhero one.
- **The platform issued a new key for the credential.** The recovery code is the
  passkey-independent factor for this case.

**Fix:** unlock with your **recovery code** or **passphrase** instead, on the same device. Both are
offered on the "this device already has a wallet" screen.

### Tapping the passkey card opens an onboarding screen instead of a biometric prompt

Your device has a wallet that unlocks with a passphrase and recovery code. The card hands off to
the wallet screen, where your passphrase opens it. You can enroll a device passkey from there.

### It says "Tap to try again" with no error

If you cancelled, or the OS dismissed the sheet, tap again.

## Connecting an external wallet

### The wallet is not detected

Superhero scans for an injected wallet over a browser message connection with a short window:

| Situation | Detection window |
| --- | --- |
| Desktop browser, user-initiated connect | 4 seconds |
| Mobile or Safari, not framed | 100 ms, failing fast to the deep-link path |
| Silent reconnect after a page refresh | 15 seconds |

The reconnect window is longer because the extension's content script can be injected after the
app has already booted.

**Fix:** confirm the extension is installed *and enabled for this site*, unlock it, then reload the
page and use Connect again. If no wallet answers and the page is not framed, the app falls back to
a deep link: `superhero://` on mobile, otherwise `wallet.superhero.com` in a new window.

### The app opened wallet.superhero.com instead of my extension

No extension answered within the detection window, so the app opened the web wallet. Apply the fix
above, or carry on in the web wallet.

### After a refresh the app shows my address but signing does not start

After a refresh the app restores a **static (read-only) account**. Signing and address-change
events run over a live RPC session.

**Fix:** click Connect again to re-establish the RPC session. The app also attempts a reconnect on
its own once per page load, when both a previously active account and persisted wallet info exist.

### The app shows "disconnected" while the extension is open

A health check runs every five seconds and clears the connection state when the SDK reports no
accounts. Press Connect again.

### Disconnect did not stick; it reconnected on refresh

Disconnecting clears the persisted session keys (`account:activeAccount`, `wallet:walletInfo`,
`wallet:balance`, `dex:recentActivities`, `liquidityPositions`), stops wallet detection and drops
the cached connection. If a reconnect happens anyway, check for a stale `?address=` query parameter
in the URL. The app consumes that parameter to install a static account, then strips it.

## Hardware accounts in Superhero Wallet

### Finding the "Add Ledger accounts" button

The button appears when the selected account is æternity **and** the surface has WebUSB, which is
a Chromium browser:

| Surface | Ledger button |
| --- | --- |
| Chrome, Brave, Opera extension | Shown |
| `wallet.superhero.com` in a Chromium browser | Shown |
| Firefox (extension or web) | Hidden; WebUSB is a Chromium feature |
| iOS or Android app | Hidden |
| A non-æternity account selected | Hidden |

**Fix:** use a Chromium browser, or switch to an æternity account first. AirGap pairing is
available on every surface.

### "Connection timed out" when importing from a Ledger

Two causes: the device is not properly plugged in, or the **æternity app is not open on it**. Plug
in over USB, open the æternity app, then press connect. The same applies when signing: the device
must be unlocked with the æternity app active.

### An AirGap QR code will not scan or decode

Set AirGap Vault to **QR code V3**, the format Superhero Wallet decodes. Every AirGap screen also
accepts the `airgap-wallet://?ur=…` string pasted by hand, which works when the camera is
unavailable.

### An AirGap account shows "Signing messages is currently not supported for AirGap accounts"

AirGap accounts sign transactions. If an æpp needs a message signature, use a non-AirGap account
for it.

## Network

### The wallet is on a different network from the app

Superhero builds are **network-pinned at build time** through `VITE_NETWORK`. The app offers the
network its bundle was built for.

**Fix:** switch networks in your wallet to match the build: `ae_mainnet` on superhero.com. For
testnet work, use a testnet build and see [Using Testnet](/getting-started/testnet).

## Balances and signing

### "Insufficient balance" when the balance looks sufficient

On a token trade, the **Max** button does not offer your whole balance. It withholds a slippage
allowance plus a flat gas reserve:

```text
max = balance − balance × (slippage + 1) / 100 − 0.001 AE
```

With the default 1% slippage that is a 2% reserve plus 0.001 AE. Separately, **gas is charged on
top of the transaction fee**, up to the gas limit, which is why the signing prompt shows a "Gas,
at most" row as well as "Network fee". The balance needs to cover the amount plus fee plus gas.

**Fix:** leave headroom for the fee and gas, or lower the amount. Keep slippage where it is.

### The signing prompt withholds the approve button

If the transaction envelope, a contract call's arguments, or a wrapped inner transaction does not
decode, the confirmation withholds approval by design, so you sign what you can read.

**Fix:** report what you were doing when it appeared.

### "no unlock prompt is mounted — refusing to sign"

The in-page signer asked for user verification and found no prompt host mounted, so it answered
immediately with a rejection. This is the fail-closed guard.

**Fix:** reload the page and retry the action. If it recurs reproducibly, report it with the exact
action.

### "derived key does not match the expected account address — refusing to sign"

The signer derived a key that does not produce the address it was installed for, and held back the
signature. The device's wallet changed under a live session (a restore or import replaced it), or an
address and index pair drifted apart.

**Fix:** reload the page so the account list is rebuilt from the current vault, then retry.

## Storage and the built-in wallet

### My built-in wallet disappeared

The encrypted vault lives in this browser's IndexedDB for this origin. Clearing site data removes
it, and Safari's Intelligent Tracking Prevention can remove it after roughly seven days without
interaction.

**Fix:** restore from your written recovery phrase, or from a **syncing** passkey if the wallet was
created by the passkey path. The passphrase and recovery code unlock the vault record on this
device, so once that record is gone, the phrase or the passkey is the way back in. The full matrix
is in [The Built-In Wallet](/wallets/built-in-wallet#site-data-and-your-backup).

### My wallet unlocks but the app does not know my address

The address list in `localStorage` was cleared while the encrypted vault in IndexedDB survived. This is a
normal outcome of some "clear site data" variants.

**Fix:** open the wallet screen and unlock once; addresses are re-derived from index 0 upward and
the list is rebuilt.

### Restoring from a passkey shows an address I do not recognise

The restore screen checks the derived address for on-chain activity before saving anything. If it
says the account has **no on-chain activity**, you very likely picked a passkey that belongs to a
*seed-phrase* wallet, which derives a valid but completely empty different wallet.

**Fix:** do not confirm. Go back and import your recovery phrase (installed app), or connect your
existing wallet instead. Confirming would save the other wallet on this device.

### Finding the "Import an existing wallet" option

Importing a seed phrase or private key is offered **in the installed app** (Add to Home Screen /
installed PWA). In a plain browser tab, "I already have a wallet" means Connect, which never asks
for your secret.

### Private browsing

If you are in Safari private mode or site data is blocked, use a normal window for anything you
intend to keep. In those modes storage reads can fail, and the app treats an unreadable address
list as "no wallet on this device".

## Reporting a problem

| What | Where |
| --- | --- |
| App, mobile app or PWA | [github.com/superhero-com/superhero/issues](https://github.com/superhero-com/superhero/issues), the same destination as the in-app "Send Feedback" button |
| API, indexer or a wrong figure in a response | [github.com/superhero-com/superhero-api/issues](https://github.com/superhero-com/superhero-api/issues) |
| Superhero Wallet (extension, app, web wallet) | The wallet's own **Report a bug** entry, at [form.typeform.com/to/Kk3Zyjdr](https://form.typeform.com/to/Kk3Zyjdr), or [github.com/superhero-com/superhero-wallet/issues](https://github.com/superhero-com/superhero-wallet/issues) |
| Security report, legal, privacy or data protection | `superherowallet@protonmail.com` |
| Chat | `chat.superhero.com` |

Include in any report:

- the **token name** or page you were on,
- your **`ak_...` address**,
- the **transaction hash** if one was produced,
- what you expected and what happened,
- for a Superhero Wallet report, the **software version and commit** from the wallet's
  More → About screen, which also shows the node and middleware versions it is talking to,
- for passkey problems, the **DOM exception name** from the browser console and the exact
  on-screen message.

Never include a private key, a seed phrase, or a screenshot showing either.
