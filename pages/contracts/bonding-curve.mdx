# BondingCurveExponential

`BondingCurveExponential.aes` computes every price in the token system. It holds no funds and
no per-community state. One instance is shared by every community, and the token sale calls
into it through the `BondingCurve` interface.

Resolve its address with `factory.bonding_curve()`. Use `BondingCurveExponential.aci.json`
when you call the curve directly; `BondingCurve.aci.json` is the interface the sale holds.

## Entrypoints

Everything here is non-stateful. The SDK dry-runs these calls by default without a network fee;
broadcasting a contract-call transaction still incurs network charges.

| Entrypoint | Signature | What it gives you |
| --- | --- | --- |
| `calculate_buy_price` | `(total_supply: int, count: int) => int` | Cost in aettos of buying `count` more tokens at a given supply |
| `calculate_sell_return` | `(total_supply: int, sell_tokens: int) => int` | AE returned for selling `sell_tokens` at a given supply |
| `buy_price` | `(total_supply: int) => int` | Ceiling of the spot ratio in AE per whole token, not a quote in aettos |
| `sell_price` | `(total_supply: int) => int` | Floor of the sell spot ratio in AE per whole token, not a quote in aettos |
| `buy_curve` | `(x: int) => Frac.frac` | The raw buy curve value as an exact rational |
| `sell_curve` | `(x: int) => Frac.frac` | The raw sell curve value as an exact rational |
| `get_k` | `() => int` | Exponent coefficient |
| `get_initial_price` | `() => int` | Spot buy price at supply 0 (`10^11` aettos, 0.0000001 AE per token); the offset `a - initial_price` is not stored |
| `get_minimum_count` | `() => int` | Smallest tradable count |
| `get_sell_return_percentage` | `() => int` | The sell factor numerator |
| `get_sell_return_precision` | `() => int` | Getter intended to expose the sell factor denominator; see the implementation note below |
| `curve_type` | `() => string` | Curve identifier |
| `supported_decimals` | `() => int` | Token decimals the curve is calibrated for |

The `BondingCurve` interface declares the same eight computational entrypoints with unnamed
arguments (`_1`, `_2`), which is why the sale contract's ACI shows them that way.

`buy_price(total_supply)` takes a supply. `calculate_buy_price(total_supply, count)` takes
both the starting supply and the count to buy, in token base units. The token sale's
`price(count)` takes only a count and reads the current supply for you.

Use `calculate_buy_price` and `calculate_sell_return` for quotes.

## Curve constants

| Constant | Sophia literal | As a number |
| --- | --- | --- |
| `a` | `1 * 10 ^ 15` | 1,000,000,000,000,000 |
| `k` | `1 * 10 ^ 10` | 10,000,000,000 |
| `initial_price` | `1 * 10 ^ 11` | 100,000,000,000 |
| `decimals` | `1 * 10 ^ 18` | 10^18 |
| `minimum_count` | `1 * 10 ^ 12` | 10^12 token base units, i.e. 10^-6 of a token |
| `sell_return_percentage` | `9950` | 99.50% |
| `sell_return_precision` | `10000` | the denominator of that percentage |
| `curve_type()` | `"TAYLOR_EXPONENTIAL_V1"` | n/a |
| `supported_decimals()` | `18` | n/a |

The closed-form curve these constants encode:

```text
buy(x)  = 0.001 * e^(0.00000001 * x) - 0.0009999
sell(x) = buy(x) * 0.995
```

## How the constants map to the formula

The contract works in fixed point against `decimals = 10^18`, so each decimal constant is
that fraction scaled by 10^18:

```text
a             = 10^15  →  10^15 / 10^18 = 0.001
k             = 10^10  →  10^10 / 10^18 = 0.00000001
initial_price = 10^11  →  10^11 / 10^18 = 0.0000001
```

`a` and `k` are the `0.001` and `0.00000001` of the closed form. The `0.0009999` offset is
`a - initial_price` (`0.001 - 0.0000001`), which is how a curve pinned to
`f(0) = initial_price` is written. So `f(0)` is `0.0000001` AE per token, not zero: the very
first token has a non-zero price.

The 0.995 sell factor is `sell_return_percentage / sell_return_precision = 9950 / 10000`.
That 0.5% is the DAO's half of the spread. The sale contract adds the other 0.5% as the
affiliation fee on the way in, which is how the round trip reaches a 1% total spread while the
curve itself only knows about 0.5%.

`get_sell_return_precision()` returns `sell_return_percentage` (`9950`), not the internal
denominator `10000` that the calculation uses. This is a getter bug in
[`BondingCurveExponential.aes`](https://github.com/bctsl/bctsl-contracts/blob/02e5dc1acb31729b7f0e4c2c72bcd9e381c9d9dc/contracts/BondingCurveExponential.aes),
and the deployed mainnet curve `ct_6E78VvU5Raz7g6oaGymF2eMNG7FjVToS6JA4AqoufaWF6sTXd` returns
`9950` from both getters. Do not derive the sell factor by dividing the two getters.

## What the contract evaluates

FATE has no floating point, so the contract replaces `e^x` with a **bounded Maclaurin (Taylor)
expansion in integer fixed point**. The closed form above is the idealised curve the contract
approximates.

`calculate_price` is a difference of two expansions:

```sophia
function calculate_price(total_supply : int, count : int) =
  require(count >= minimum_count, "MINIMUM_TOKENS_REQUIRED")
  let current_supply_exponent = (k * total_supply)
  let next_supply_exponent    = (k * (total_supply + count))
  (initial_price * count) / decimals
    + ((a * (mc2(next_supply_exponent) - mc2(current_supply_exponent))) / (k * decimals))
```

`mc2(x)` is the Maclaurin series for `e^x` starting at the quadratic term. It omits the
`1` and the `x` term, because those cancel in the difference and are folded into the
`initial_price * count / decimals` term:

```sophia
function mc2(x : int) = exp_helper(x, x, 0, 2, decimals * decimals)

function exp_helper(x : int, term : int, sum : int, i : int, scale : int) : int =
  if (i > 100 || term < 1)
    sum
  else
    let next_term = (term * x) / (i * scale)   // x^i / i!
    exp_helper(x, next_term, sum + next_term, i + 1, scale)
```

Two things bound the series:

- **A hard cap of 100 iterations.** The recursion stops once `i > 100`, so at most 99 terms
  (i = 2 through 100) are ever summed.
- **Integer truncation.** Every term is an integer division by `i * scale` with
  `scale = decimals^2 = 10^36`. The series stops as soon as `term < 1`, because a term that
  truncates to zero makes every later term zero too. At realistic supplies this fires long
  before the iteration cap.

For a count of 1,000 whole tokens, the integer calculation differs from the idealised integral
by less than one aetto at starting supplies 0 and 10,000,000. This is a check of those
examples, not a bound for arbitrary inputs. Use the closed form for explanation and
`calculate_buy_price` for a transaction quote.

`calculate_price` carries the only `require` on the curve: a `count` below `minimum_count`
(10^12 token base units) aborts with `MINIMUM_TOKENS_REQUIRED`. That applies to `calculate_buy_price` and
`calculate_sell_return` alike, because both route through it.

`buy_curve` and `sell_curve` are a separate code path. They call `exp_helper` with the full
series from `i = 1`, including the constant term (`exp_helper(x_exponent, decimals, decimals,
1, decimals)`), and return a `Frac.frac` rather than an integer. They give you the
instantaneous curve value for charting; they are not what a trade is priced from.

## The `Frac.frac` type

```sophia
datatype frac = Pos(int, int) | Zero | Neg(int, int)
              //  numerator, denominator
```

`Frac` is the æternity standard library's exact rational type. A value is either `Zero` or a
signed numerator/denominator pair. Decoded in JavaScript it is a one-key object:

```javascript
const value = await curve.buy_curve(supply).then((r) => r.decodedResult);
// { Pos: [ 123456789n, 1000000000000n ] }   or   { Zero: [] }   or   { Neg: [ n, d ] }
```

Keep it as a ratio of BigInts until the last possible moment. Never build a JavaScript
`Number` out of either half, because both can exceed 2^53:

```javascript
import BigNumber from 'bignumber.js';

function fracToBigNumber(frac) {
  if ('Zero' in frac) return new BigNumber(0);
  const [num, den] = 'Pos' in frac ? frac.Pos : frac.Neg;
  const value = new BigNumber(num.toString()).dividedBy(den.toString());
  return 'Neg' in frac ? value.negated() : value;
}
```

For anything that touches money, do not convert at all. Call `calculate_buy_price` or
`calculate_sell_return`, which return integer aettos computed on chain. `buy_curve` and
`sell_curve` are for charting and analysis, where a rounding error of one part in 10^18 does
not matter.

## Reading the live constants

```javascript
const curveAddress = await factory.bonding_curve().then((r) => r.decodedResult);

const curve = await Contract.initialize({
  aci: JSON.parse(fs.readFileSync('./contracts/BondingCurveExponential.aci.json', 'utf8')),
  address: curveAddress,
  onNode: aeSdk.api,
});

console.log({
  k: (await curve.get_k().then((r) => r.decodedResult)).toString(),
  initialPrice: (await curve.get_initial_price().then((r) => r.decodedResult)).toString(),
  minimumCount: (await curve.get_minimum_count().then((r) => r.decodedResult)).toString(),
  sellPct: (await curve.get_sell_return_percentage().then((r) => r.decodedResult)).toString(),
  curveType: await curve.curve_type().then((r) => r.decodedResult),
  decimals: (await curve.supported_decimals().then((r) => r.decodedResult)).toString(),
});
```

## Practical notes

- **Price is a pure function of supply.** There is no time component, no oracle and no
  liquidity provider. Two buys of the same size at the same supply cost the same.
- **`minimum_count` is 10^12 base units.** With 18-decimal tokens that is 0.000001 of a token.
  Calls below it abort with `MINIMUM_TOKENS_REQUIRED`.
- **Price grows exponentially with supply.** Use the actual supply and trade size when
  calculating a quote; this curve does not define a maximum token supply.
- **Integer quotes do not prove aggregate solvency.** Separately rounded trade quotes need not
  sum to the quote for their combined amount. See
  [Reserve accounting and rounding](/concepts/value-flow#reserve-accounting-and-rounding) for the
  continuous-model redemption argument and its implementation limits.
