# The DAO Treasury

A community DAO holds plain AE. The treasury is the AE balance of the `DAO` contract, and it
leaves through a payout vote that passes and is applied in time.

## Where the money comes from

| Source | Amount | Path into the DAO |
| --- | --- | --- |
| Buys on the bonding curve | 0.5% of the curve value of every buy | `record_sale_transaction(buyer, buy_price)` |
| Opening a proposal | 555 AE per vote opened | `add_vote(metadata)`, which is payable |
| A `ChangeDAO` migration into this DAO | The whole balance of the old DAO | `Chain.spend` from the old DAO |

Those are the three sources. The 1% spread is charged on the buy side, so sells carry no DAO
share; tips and posts settle through `Tipping_v3`, outside the token sale.

The DAO's share is not computed as a percentage. The sale sets the redemption reserve aside
first and forwards what is left:

```sophia
let reserve = state.bonding_curve.calculate_sell_return(state.token_contract.total_supply(), count)
state.dao_contract.record_sale_transaction(
  value = Call.value - overpaid_refund - affiliation_amount - reserve, protected = true, ...)
```

`total_supply()` has already been incremented by the mint, so `reserve` is exactly `0.995 ×`
the curve price and the DAO receives the residual `0.5%`. Setting the payout obligation aside
before the treasury is paid is what keeps the reserve solvent.

The call is `protected = true`, so a trade completes even if the DAO call aborts; the AE then
stays in the sale contract. See [Value flow](/concepts/value-flow) and
[Fees & Slippage](/tokens/fees-and-slippage).

## `record_sale_transaction`

```text
stateful payable entrypoint record_sale_transaction(buyer: address, buy_price: int) : unit
```

The AE rides along with the call; the buyer's address and the buy price arrive as arguments.
The stock DAO keeps the AE and does not store the arguments. Reconstruct which buys funded a
treasury from the `Buy` events on the sale contract. The entrypoint is part of the
`ReplaceableDAO` interface, so a replacement DAO can split income, forward part of it, or
account for it per buyer. See [Replaceable DAOs](/dao/replaceable-dao).

The token sale also calls `record_sale_transaction` with zero value and placeholder arguments
as a probe, at deployment and on every `set_beneficiary`, to check the entrypoint exists. A
DAO must accept zero-value calls to be a beneficiary.

## The 555 AE contribution

The 555 AE paid on `add_vote` is a contribution to the DAO. It lands in the treasury and stays
there whatever the outcome: on rejection, on expiry and on success alike.

- The treasury grows every time somebody proposes something.
- Opening a proposal commits 555 AE to the community, so prepare the proposal and its support
  before you open it.
- Apply a passed vote within the roughly two-day execution window; a proposal that expires is
  opened again with a new 555 AE contribution.

## Read the balance

### On-chain

The treasury is the AE held at the DAO's contract address. Take that address from the token's
`dao_address` field, then look it up on [æScan](https://aescan.io) or with your SDK's balance
call for a contract address.

Everything else about the DAO is read through its entrypoints:

| Read | Returns |
| --- | --- |
| `get_state()` | The whole `DAO.state` record |
| `votes()` | Every vote, keyed by sequential id, with an applied flag |
| `vote_timeout()` | The execution window, in key-blocks |
| `get_token()` | The community AEX-9 token contract |
| `get_token_sale()` | The sale contract this DAO owns |
| `get_community_management()` | The linked `CommunityManagement`, as an option |
| `factory()` | The factory that deployed it |

### Through the Superhero API

`GET /api/tokens/{address}` returns the token DTO, which carries the treasury directly:

| Field | Meaning |
| --- | --- |
| `dao_address` | The DAO contract address for this token |
| `dao_balance` | The treasury balance, as a string in aettos |
| `sale_address` | The token sale contract, used as the route key in the app |
| `total_supply` | Needed to evaluate the 10% participation quorum |
| `holders_count` | How many addresses hold the token |

`dao_balance` is in aettos; divide by `10^18` to get AE. See
[Tokens API](/api-reference/tokens) for the rest of the DTO.

`dao_balance` is refreshed together with the token's live price, so it is as fresh as the last
price refresh. For a balance consistent with a specific block (for example, when checking
whether a `VotePayoutAmount` proposal is affordable), read the contract's account balance at
that height yourself.

## The treasury in the app

| View | Route | What it shows |
| --- | --- | --- |
| DAO list | `/trends/daos` | Every community DAO as a card: treasury balance, holders, creation date, market cap. Sortable and searchable. |
| One DAO | `/trends/dao/:saleAddress` | That community's treasury, its proposal list, and the create-vote form. |
| One proposal | `/trends/dao/:saleAddress/vote/:voteId/:voteAddress` | The ballot, the voters table, and the vote, revoke, withdraw and apply actions. |

The DAO list is keyed by `sale_address`, not by the DAO address, because the sale contract is the
stable public identifier for a community across the app.

## What the treasury can be spent on

Two of the seven vote subjects move money:

- `VotePayout(recipient)` sends the **entire** DAO balance to one account.
- `VotePayoutAmount(recipient, amount)` sends a **specified** amount to one account.

Each payout goes to one account. To split a grant between three contributors, run three
proposals, or pay one address that then distributes. A `ChangeDAO` vote also moves the whole
balance, as part of a migration; see [Replaceable DAOs](/dao/replaceable-dao).
