# Moderation

Posts and comments on Superhero belong to their authors and stay on chain, where anyone can
verify them. Moderation happens at the **community application layer**, through token-holder
governance: moderators control access to a community's chat room, and token holders set the
threshold for writing in the community and for opening a DAO vote.

## CommunityManagement.aes

Each community gets its own `CommunityManagement` contract, deployed by the factory during
community creation.

### State

| Field | Type | Meaning |
| --- | --- | --- |
| `owner` | `address` | The contract owner; set to `Call.caller` at `init`, transferable with `set_owner` |
| `minimum_token_threshold` | `int` | Raw base-unit token balance required for write access in this community |
| `is_private` | `bool` | Whether the community is private |
| `moderator_accounts` | set of `address` | The current moderator set |
| `muted_user_ids` | set of `string` | Muted identifiers: `ak_…` addresses held as strings |
| `meta_info` | map of `string` to `string` | Community metadata |

### Entrypoints and who may call them

Two guards cover every write:

```sophia
function require_owner() =
  require(Call.caller == state.owner, "ONLY_OWNER_CAN_CHANGE")

function require_moderator() =
  require(Set.member(Call.caller, state.moderator_accounts), "ONLY_MODERATOR_CAN_CHANGE")
```

| Entrypoint | Signature | Guard |
| --- | --- | --- |
| `get_state` | `() => CommunityManagement.state` | read |
| `moderator_accounts` | `() => Set.set(address)` | read |
| `muted_user_ids` | `() => Set.set(string)` | read |
| `minimum_token_threshold` | `() => int` | read |
| `owner` | `() => address` | read |
| `meta_info` | `() => meta_info` | read |
| `version` | `() => int` | read; returns `1` |
| `mute_user_id` | `(user_id: string) => unit` | `require_moderator` |
| `unmute_user_id` | `(user_id: string) => unit` | `require_moderator` |
| `add_moderator` | `(moderator: address) => unit` | `require_owner` |
| `delete_moderator` | `(moderator: address) => unit` | `require_owner` |
| `change_minimum_token_threshold` | `(minimum_token_threshold: int) => unit` | `require_owner` |
| `change_meta_info` | `(meta_info: meta_info) => unit` | `require_owner` |
| `set_owner` | `(owner: address) => unit` | `require_owner` |

Every write emits a typed event first, then applies: `MuteUserId(string)`,
`UnmuteUserId(string)`, `AddModerator(address)`, `DeleteModerator(address)`,
`ChangeMinimumTokenThreshold(int)`, `SetOwner(address)` and `ChangedMetaInfo`.

The contract checks the owner, not the DAO; the DAO is whoever the owner is.

### Who owns it, and who the first moderator is

`CommunityFactory.create_community` settles both in one transaction:

```sophia
let community_management = Chain.create(Call.caller, 10 ^ decimals(), is_private, meta_info) : CommunityManagement
let dao = Chain.create(None, Contract.address) : DAO
...
community_management.set_owner(dao.address)
```

| Question | Answer |
| --- | --- |
| Initial owner | The **factory**, because `init` sets `owner = Call.caller`, then reassigned to the DAO in the same transaction by `set_owner` |
| Final owner | The community's **DAO** contract |
| Initial moderator | The account that called `create_community`, the community's creator |
| Initial `minimum_token_threshold` | `10 ^ decimals()` with `decimals() = 18`, so **one whole token** in raw base units |
| Initial `muted_user_ids` | Empty (`Set.new()`) |
| `is_private` | Exactly the boolean passed to `create_community` |

The creator gets the first moderator seat, and the DAO gets everything else.

### Changing the owner

`set_owner` requires the current owner, which is the DAO. The DAO exposes one route to it: the
`ChangeDAO` vote subject, which moves the token sale's beneficiary and owner to a replacement
DAO and then calls `community_management.set_owner(new_dao_address)`. It first requires that
the replacement references the same `CommunityManagement` instance
(`NEW_DAO_HAS_TO_REFERENCE_SAME_COMMUNITY_MANAGEMENT`), so a `ChangeDAO` vote always keeps the
community's own moderation contract.

## Who can do what

| Action | Who | How |
| --- | --- | --- |
| Mute a user id | A moderator | A direct call to `mute_user_id` |
| Unmute | A moderator | `unmute_user_id` |
| Appoint a moderator | Token holders | An `AddModerator` DAO vote, applied to the contract |
| Remove a moderator | Token holders | A `DeleteModerator` DAO vote |
| Change the write threshold | Token holders | A `ChangeMinimumTokenThreshold` DAO vote |
| Change community metadata | Token holders | A `ChangeMetaInfo` DAO vote |
| Replace the owner | Token holders | A `ChangeDAO` vote, which reassigns `set_owner` |

Moderators act directly within their mandate; the mandate itself is granted and revoked by
vote.

### The vote that appoints a moderator

Moderation changes ride the same DAO machinery as treasury payouts:

| Rule | Value |
| --- | --- |
| Who may open a vote | A holder with at least the community threshold of tokens |
| Cost to open | 555 AE, paid to the DAO |
| Voting period | Two weeks, measured in key-blocks |
| Approval required | At least 55% of the vote stake in favour |
| Quorum | At least 10% of the total token stake participating |
| Execution window | Roughly two days after the vote closes |
| Who executes | Anyone. Any account or script can trigger the application |

Tokens used to vote are locked by the vote contract via the AEX-9 allowance mechanism and can
be reclaimed with `revoke_vote` before the close or `withdraw` after it. The 555 AE goes to the
DAO whether or not the vote passes.

Appointing a moderator therefore takes two weeks and 555 AE.

The app's create-vote form covers five of the seven vote subjects: payout, change DAO, change
the minimum token threshold, add moderator, delete moderator. Open a `VotePayoutAmount` or
`ChangeMetaInfo` proposal through the SDK or a direct contract call; see
[Proposals and Vote Subjects](/dao/proposals).

## What a mute does

A `user_id` is the holder's `ak_…` account address held as a string. The token-gated-rooms
pipeline enforces it:

1. The API reads `CommunityManagement.get_state()` and mirrors `muted_user_ids` into the room's
   muted list, alongside `moderators`, `min_token_threshold`, `is_private` and the owner
   address. The relay's admin and role lists are derived from the same read.
2. Eligibility for the room is `balance >= min_token_threshold AND NOT muted`, where the muted
   check compares the member's æternity address against that list.
3. A muted member is removed from the relay group with a kind-9001 event, and the sync skips
   the kind-9000 add for any member currently muted, so a mute holds across re-syncs.

Mute a holder and they become ineligible for that community's chat room regardless of balance,
until the mute is lifted.

A mute governs chat-room eligibility. Posts, comments, topic feeds and the popular ranking are
independent of `muted_user_ids`: a muted account's posts stay visible, and it can continue to
post.

The per-room mute in the chat app is a *notification* preference: it silences your own alerts
for that room. See [Notifications](/social/notifications).

## The write threshold

`minimum_token_threshold` is a raw base-unit token balance, and it gates two things:

| Gate | Where | Rule |
| --- | --- | --- |
| Opening a DAO vote | `DAO.add_vote` | `token.balance(Call.caller) >= minimum_token_threshold`, else `ADD_VOTE_TOKEN_HOLDER_MISSMATCH` |
| Entering the community chat room | The rooms eligibility check | raw balance `>=` raw threshold, and not muted |

It starts at one whole token (`10 ^ 18`) and changes through a `ChangeMinimumTokenThreshold`
vote. The same value surfaces in the chat rooms API as `min_token_threshold`, alongside the
room's `is_private` flag. A holder's room list shows the rooms they are eligible for, and the
composer shows a "hold the token" gate for the rest. See [Chat](/social/chat).

## The privacy flag

`create_community(collection_name, name, initial_buy_count, is_private, meta_info)` passes
`is_private` straight into `CommunityManagement`'s `init`, and the rooms service reads it back
out of `get_state()` unchanged. The community's on-chain privacy flag and the chat room's are
the same value, chosen once at creation.

## The scope of a mute

- **A mute is a chat-room membership control.** It is held per community, in that community's
  own `CommunityManagement` instance.
- **It applies to the muted account's room access.** Posts and comments are on-chain records
  owned by their authors; they stay in place and anyone can verify them.
- **The Superhero API and the relay it controls enforce the list** for the community's room.

## Hiding your own post

To hide one of your own posts from the feeds, include a media entry whose text contains
`hidden`. The indexer sets `is_hidden` from the post's media list at index time, which removes
the post from the feeds and from popular ranking. It is a convention an author applies to their
own post; the post stays on chain.
