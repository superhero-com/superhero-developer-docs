# Identity and DIDs

A SuperheroID is an æternity address plus the provider links attached to it in the
`AddressLink` contract. There is no separate identifier scheme: the `ak_…` address is the
identifier, the Ed25519 key it encodes is the verification material, and the links are the
claims. For readers who know
[Decentralized Identifiers (DIDs) v1.0](https://www.w3.org/TR/did/), the model maps onto DID
Core concepts like this:

| DID Core concept | Superhero equivalent |
| --- | --- |
| DID subject and controller | The æternity account, an `ak_…` address |
| Verification method | The Ed25519 public key the address encodes; signatures verified on chain with `Crypto.verify_sig` |
| Authentication | Wallet signed messages, using the æternity signed-message prefix, with a contract-held nonce |
| `alsoKnownAs` | The `x`, `nostr` and `prefaens` links in `AddressLink` |
| Service endpoint | The `nostr` key used for chat; the `site` link |
| Verifiable data registry | `AddressLink` state plus AENS |
| Update and deactivate | `link` and `unlink`, per provider |

`AddressLink` also accepts `did:ae:<subject>` through `link_did`, `resolve_did_controller`
and related entrypoints. The subject must be the signer's address or a `.chain` name the signer
owns. These calls share the signer's ordinary links and nonce, although the Superhero API does
not index changes made through them. They do not supply DID documents or by themselves
establish DID Core compliance. See [AddressLink](/identity/address-link).

## Verifying a SuperheroID

1. **Prove control of the address.** Ask for a signed message and verify it against the `ak_…`
   public key using the æternity signed-message construction.
2. **Check a `.chain` name.** Resolve it through AENS on any node or middleware and compare its
   `account_pubkey` pointer to the address. Check ownership separately: `prefaens` linking
   verifies the AENS owner with `AENSv2.lookup`, not the account pointer. Owners can point
   their names at a different account.
3. **Read the links.** `AddressLink.get_links(addr)` returns the provider-to-value map as a
   dry-run call, and `resolve(provider, value)` walks it backwards. Both are free reads against
   consensus state.
4. **X handle.** The chain records the address's consent to a handle string; the OAuth check
   was performed by Superhero's backend. See
   [Verifying Your X Account](/identity/x-verification).
5. **Authorship of content.** For direct posts, the `Tipping` contract records the caller as
   author. For delegated posts, it verifies the author's message signature while a separate
   relayer signs and pays for the transaction. See [Delegated posting](/social/delegated-posting).
